About this course

Most of the information a business keeps lives in tables, and SQL is the language used to put a question to a table. A shop's orders can be searched for the largest, the customers who have never bought anything can be listed, and this month's sales can be set beside last month's, all with queries a few lines long, which is why people who work with data in shops, schools and hospitals write them every day.

The course follows the records of one small shop. The second part reduces many rows to a count, a total or a group, and says what happens to the values that are missing. The third part joins tables together, so that an order can be read beside the customer who placed it, and the fourth ranks and compares rows without discarding any of them.

The same few tables appear in every lesson, so that you come to know the data and can give your attention to the new idea. Know what a row represents

Opener

Take the query SELECT name FROM customers. On the shop's customers table it returns four names, one for each person who has signed up. On a table that holds one row for each sale it would return the same kind of list, but Ada would appear twice if she had bought twice, and counting the rows would count purchases instead of people.

Telling two rows apart

A row needs a name, because two rows can hold the same facts. Suppose a school keeps a list of its students, and two of them are both called Sam. If the only way to refer to a student were by name, nobody could say which Sam they meant.

The fix is a column that holds a different value in every row. A school would give each student a number and record it in a column called id. A column like that is called a primary key, because it names each row exactly once. In the shop's tables the primary key is always the column called id, so Ada is customer 1 and Ben is customer 2 whatever else about them changes.

Most columns are allowed to repeat. Two customers can live in the same region and the table is no worse for it. Only the key has to differ from row to row, and that matters in a moment, when a second table needs a way to point at a row of the first.

A condition that follows the stored reference pairs the right rows. A condition that compares two columns which happen to hold similar numbers pairs the wrong ones, and the query still runs.

In the school lists, a pupil's club column holds the number of a club, so p.club = c.id follows the reference. Each pupil also has an id of their own, and p.id = c.id compares a pupil's id with a club's id. Both columns hold small numbers, so the second query does return rows. Some of them are wrong.
