Teaching

An assignment stores a value under a name

Take the line price = 4. Python works out whatever stands to the right of the equals sign, which here is simply the number 4, and stores the result under the name on the left, so that any later line can ask for price and get 4 back. A line that does this is called an assignment. The single equals sign is an instruction to store a value and not a claim that two things are equal, because Python writes a test for equality with a double sign, ==, which comes later in the course.

The right-hand side is always worked out first and in full. In total = price * 3, Python looks up price, multiplies the value it finds by 3, and only then stores the product, so the name on the left receives a finished value and not a recipe for calculating it.

Python also lets you leave notes for the reader. Anything after a # sign on a line is a comment, and Python skips it entirely, so a line such as # price = 100 changes nothing about what price holds.

A notebook keeps its names between cells

Much data analysis is done in a notebook, a document that mixes code with its results and is divided into cells, each holding a few lines of code that you run one at a time. Running a cell sends its lines to a program called the kernel, which carries out the Python and holds every name created so far, so that a name set in one cell can be used by any cell you run afterwards.

The kernel remembers what has been run and not what is written on the page. If you edit a cell and do not run it again, the kernel still holds the values from the last run, and if you run cells in a different order from the one in which they appear, each name holds whatever the latest run left behind. Restarting the kernel clears every name, and that is why a notebook is only trustworthy once it has been restarted and run again from the top.

The order of the runs is part of the program

Two notebooks with identical cells can end in different states, because the kernel records the order in which cells were run and not the order in which they are written. Suppose cell 1 sets width = 3, cell 2 sets area = width * 2, and cell 3 sets width = 8. Run in that order, the cells leave area at 6. A notebook is therefore reproducible only if it gives the same results when the kernel is restarted and every cell is run once, from the top, in order. Before you share a notebook, restart the kernel and run all the cells: any cell that fails, or that changes a result, was relying on a run the page does not show.

Why the order of runs matters

Because the kernel remembers, the order in which you run cells decides what it holds, and that order need not match the order down the page. Say cell 1 sets days = 3 and cell 2 works out hours = days * 24, so hours is 72.

Now go back and edit cell 1 to days = 5, and run only that cell. The kernel holds days at 5, but hours is still 72, because the line that works it out has not run again. Run cell 2 and hours becomes 120. Until you do, the page shows code that no longer matches what the kernel holds.

This is why a notebook can mislead. The page can look right while the kernel holds results from older runs. The check is to restart the kernel and run every cell from the top, in page order. If the results still make sense, nothing in the notebook depends on an old run.

Decimals are stored approximately, whole numbers exactly

A floatA number with a decimal point, such as 3.4. Met in 'Python divides in three ways'. is stored in binary, and most decimal fractions cannot be written exactly in binary, in the same way that one third cannot be written exactly with a finite number of decimal digits. Python therefore stores the nearest value it can, and a sum of floats can come out a very small distance from the decimal answer you expect. The error is far too small to matter in a total, but it is large enough to matter when two floats are compared with ==, because == asks whether the stored values are identical and not whether they are close.

Whole numbers have no such problem. An int is exact whatever its size, since Python widens it as needed, and so counts of rows or of people should stay as ints. The practical rule for floats is to compare them after rounding, or within a tolerance, and never to trust == on the result of decimal arithmetic.

Decimals are approximate

Back to / for a moment. Its answers are floats, and floats have a limit you should know about before trusting them with money. A computer stores a float using only 0s and 1s, and in that system some decimals have no exact form, just as one third has no exact decimal form: 0.333 and so on without end. The decimal 0.1 is one of the awkward ones. Python keeps the nearest value it can, which is very slightly off.

Usually the error is far too small to see. It shows when you compare. The symbol == asks whether two values are equal and answers True or False, a value of type bool. The sum 0.1 * 3 comes out as 0.30000000000000004, so 0.1 * 3 == 0.3 is False even though the two sides agree on paper. That is why money is often held in whole pence, and why exact comparisons of floats are avoided.

Whole numbers have no such problem. An int is stored exactly, and it can grow as large as the computer's memory allows.

A table of sales has a row for Hill with nothing in its units column. The shop may have sold nothing, so that the true value is zero, or it may have sent no figure, so that the true value is unknown, and an empty cell in a spreadsheet does not say which. A calculation that treats the unknown as zero reports a lower average, while one that skips it reports the average of the shops that did report.

pandas keeps the unknown apart from zero, which gives you a choice to make and to state. This lesson shows how to find and count the gaps, what the default summaries do with them, and how filling, dropping and flagging each change the answer.

By the end you'll be able to find and count missing values, say what a mean does with them, and choose and keep a cleaning step.

Previous text

A gap is easy to mishandle. Treated as a zero, it says the fourth person has no pets, which nobody told us. Skipped over, it quietly changes an average. What pandas does with a gap, and what you can do about it, decides whether the numbers you report mean what you think they do.

This lesson follows that one blank through counting, averaging, filling and dropping, and ends by checking that a clean-up was actually kept.

By the end you'll tell a missing value from a zero, and say how a cleaning choice changes a count or a mean.

Finding the blanks

Averages leave the blanks out

Now the survey needs an average. pandas does not wait for you to deal with the gaps first. s.mean() adds up the known entries and divides by the number of known entries, so a gap leaves out both its value and its place in the count. For the answers 7, a gap and 11, the mean is (7 + 11) ÷ 2 = 9, and s.count() is 2.

Teaching

A cleaning step that is not stored changes nothing

Both fillna and dropna return new objects and leave the original alone, in the way the string methods did. The line cleaned = df['u'].fillna(0) creates a cleaned column and leaves df['u'] with its gaps, so a later calculation on df['u'] still sees them. To keep the cleaned values, assign the result back with df['u'] = df['u'].fillna(0), or store it under a clearly named new column, which is the better choice when the original gaps may be needed again.

The same holds for dropna: df.dropna() on a line of its own shows a result and then discards it. Every cleaning step is therefore a pair, the call that produces the cleaned data and the assignment that keeps it, and a missing assignment is the commonest reason a cleaning step seems to have had no effect.

A repeated key on both sides multiplies the rows

A merge produces one row for every pairing of a left row with a right row that shares its key. If each key appears once on the right, as in a lookup table, each left row finds at most one partner and the row count cannot grow; this is called a many-to-one merge. If a key appears several times on both sides, every left row pairs with every right row and the count multiplies, so that a key with 4 rows on the left and 3 on the right produces 4 × 3 = 12 rows.
